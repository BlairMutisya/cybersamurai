The parent build pins Java 21, Spring Boot 3.3.5, and Spring Cloud 2023.0.3. Its modules make the intended ownership visible: common contracts, API gateway, authentication, customer, account, transaction, ledger, audit, and ESB.

The problem I am working through

Banking systems fail when boundaries exist only in diagrams. Customer identity, accounts, transfers, ledger entries, audit history, and external integration have different invariants and failure modes. The first engineering objective is therefore not feature volume; it is making those responsibilities explicit enough that persistence, security, and messaging can be added without collapsing everything into a distributed monolith.

Current request path

Implemented foundation
Client→Service Controller→Shared Contract→Placeholder Response

The current controllers expose health and command-shaped endpoints. Two decisions already appear in their contracts: the ESB returns correlation-aware responses, and transfer requests require an Idempotency-Key. They are interface decisions, not yet complete business guarantees.

Target architecture

Planned — not presented as shipped
Clients→Gateway + Auth→Customer / Account / Transaction→Ledger + Audit→ESB Boundary

The target puts authentication and tenant context at the edge, keeps transactional ownership inside the relevant service, records immutable financial movements in the ledger, and uses the ESB for external integration. Asynchronous events will be introduced only where they improve decoupling without weakening the business invariant.

Honest boundary: database entities, tenant isolation, Kafka consumers, Camel routes, and automated tests are not yet present in the public Phase‑1 source. They are the next proof points, not completed claims.

Why the transfer contract starts with idempotency

A transfer endpoint can time out after the server has accepted work but before the client receives a response. Retrying without a stable business key can create duplicate effects. Requiring the key at the HTTP boundary makes the expected guarantee visible early; the next step is a durable claim table that atomically records the key, request fingerprint, processing state, and final result.

Build sequence

  1. Persistence and migrations. Add explicit entities, database ownership, and repeatable schema changes per service.
  2. Tenant context. Propagate an authenticated tenant identifier and enforce it in queries, caches, events, logs, and audit records.
  3. Ledger invariant. Model balanced entries and place transfer state plus ledger effects inside deliberate transaction boundaries.
  4. Integration routes. Replace placeholder ESB dispatch with observable Camel routes and controlled failure handling.
  5. Async delivery. Introduce Kafka with an outbox, idempotent consumers, bounded retries, and a replayable DLQ.
  6. Verification. Add unit, integration, contract, and failure-path tests before describing any capability as production-ready.

What this project demonstrates now

  • Breaking a financial domain into explicit module boundaries.
  • Version-pinned Java and Spring platform foundations.
  • Correlation and idempotency as first-class API concepts.
  • The discipline to distinguish current source from target architecture.
