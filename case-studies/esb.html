ESB Foundation: Designing the Integration Boundary Before the Routes

The ESB module currently proves a small, correlation-aware WebFlux boundary. The target is a reliable routing layer with explicit validation, transformation, retry, and dead-letter behavior.

Evidence: inspect the public ESB module ↗

The module exposes a health endpoint and a route-key dispatch endpoint. Dispatch accepts a request, preserves or creates a correlation ID, and returns a shared response contract. It is intentionally a placeholder at this stage.

The integration problem

Point-to-point integrations accumulate protocol differences, duplicated mapping rules, inconsistent error handling, and little shared observability. An integration boundary should normalize those differences while keeping business ownership inside the core services. It should not become a second application layer containing every domain rule.

Architecture progression

Current
HTTP request→Validate→Correlation ID→Accepted response
Target
Protocol Adapter→Canonical Command→Camel Route→Kafka / Service→Retry or DLQ

The target route will validate at entry, normalize protocol-specific payloads into a canonical command, attach correlation and idempotency metadata, and route the work according to its delivery requirements. Transient failures receive bounded exponential backoff; permanent failures fail fast; exhausted work is isolated with enough context for controlled replay.

Reference Camel route specimen

Scope: this is an original reference implementation for the next project phase. It is not copied from confidential client work and is not yet part of the public repository.
PaymentDispatchRoute.javaREFERENCE / TARGET
import org.apache.camel.builder.RouteBuilder;
import org.apache.camel.support.processor.idempotent.MemoryIdempotentRepository;

public final class PaymentDispatchRoute extends RouteBuilder {
  private final PaymentNormalizer normalizer;

  public PaymentDispatchRoute(PaymentNormalizer normalizer) {
    this.normalizer = normalizer;
  }

  @Override
  public void configure() {
    errorHandler(deadLetterChannel("kafka:payment.dispatch.dlq")
        .useOriginalMessage()
        .maximumRedeliveries(3)
        .redeliveryDelay(500)
        .useExponentialBackOff()
        .backOffMultiplier(2));

    from("direct:dispatch-payment")
        .routeId("dispatch-payment-v1")
        .validate(header("correlationId").isNotNull())
        .idempotentConsumer(
            header("correlationId"),
            MemoryIdempotentRepository.memoryIdempotentRepository(10_000))
        .bean(normalizer, "toCanonicalCommand")
        .setHeader("eventType", constant("payment.dispatch.requested.v1"))
        .to("kafka:payment.dispatch.v1");
  }
}

What the specimen proves

  • Bounded recovery: three redeliveries with exponential delay, followed by an explicit dead-letter destination.
  • Traceability: the route rejects messages without correlation metadata.
  • Duplicate protection: the specimen demonstrates idempotent consumption. A production route should replace the in-memory repository with durable storage.
  • Canonicalization: transport-specific input is converted before publishing a versioned event.
Production hardening would add exception classification, jitter, durable idempotency, schema validation, OpenTelemetry spans, metrics by route and exception, payload redaction, and an audited replay workflow.

Next proof points

  1. Add Camel dependencies and replace placeholder dispatch with one tested route.
  2. Persist idempotency claims so protection survives restarts and multiple instances.
  3. Add Kafka through Docker Compose with versioned contracts and a controlled DLQ.
  4. Test transient, permanent, duplicate, timeout-after-commit, and replay scenarios.
  5. Expose route latency, retry count, DLQ depth, and oldest failed-message age.

Engineering position

A good ESB is not impressive because it connects many boxes. It is valuable because failure semantics, evidence, and ownership remain clear when those connections stop behaving.
